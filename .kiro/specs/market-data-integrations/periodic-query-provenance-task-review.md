## Image and catalog ordering

No build dependency is hidden in task 3's claimed acceptance. The accepted `catalog_cli.py` requires `--image`, captures the schema from that image and verifies its source label. The draft correctly defers that canonical invocation to task 4. Task 3 instead uses the identified installed source/native inputs and clean accepted generator components to form a proposal, explicitly without image-backed acceptance. Task 1 freezes the exact runnable inputs; the historical preview script is a clean-input pattern, not an instruction to run its old image or revision unchanged.

The inspected `prototype.yml` builds in the candidate job and then automatically publishes through `alpha_cli`; it does not pause for the later controller catalog check. Accordingly, task 4's comparison is a gate on release acceptance after publication, as written, not a promised prepublication check. Drift or a blocked packaged check leaves delivery open. The draft does not need a workflow redesign or a second milestone dispatch to express that boundary.

The image embeds runtime widget/app inputs, while canonical provenance also identifies the resulting image. Promotion after the build cannot retroactively alter packaged bytes. The draft's matching-output, unchanged-consumer and exact-image checks must therefore be applied to the actual image and its original runtime inputs; a later provenance/evidence commit is not a new image. The existing no-drift acceptance condition is sufficient for this metadata-only repair. A real runtime-contract change would invalidate that condition rather than justify silently accepting the old package.
