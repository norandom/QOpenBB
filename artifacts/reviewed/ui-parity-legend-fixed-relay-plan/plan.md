# Review a fixed-target relay before another topology probe

Propose one test-only TCP relay so the original app keeps its sole internal network while the owned host client reaches a loopback origin. This is a proposal, with no implementation or runtime grant. The completed diagnostic observed configured loopback publication but null runtime allocation at three reads of one running app. Its [independent evidence review](../ui-parity-legend-startup-diagnostic-runtime-review/review.md) establishes that observation, not a general network cause. The [frozen Moby diagnosis](../ui-parity-internal-network-source-diagnosis/report.md), commit `6a43e3d5afddf4111da0f864bbc7cae5d7e95001`, supplies the separate source explanation and version limits; its independent source review is pending. It does not attest the local daemon binary or prove this relay transport.

Override the relay container's entrypoint with that Python path and a frozen read-only script using only stdlib sockets/selectors. Source support is not exact-image executable verification; missing interpreter or incompatible flags must fail the separately reviewed probe without fallback. ## One destination and one ingress

The flow is owned host loopback → relay on an ordinary ingress bridge → exact app internal IPv4:3000 on the shared internal bridge. The app joins only the internal bridge and publishes no host port. Only the relay joins both bridges and publishes `127.0.0.1::<relay-port-3100>`. No original application/UI file or production Compose setting changes.

Create both randomly named labeled networks and the app with existing disposable-state/credential ownership. Admit the exact running app's numeric IPv4 from its one owned internal attachment. Write that address and fixed port 3000 once into an immutable, hash-recorded relay config. Create the relay on the ordinary ingress bridge with its loopback publish, attach its internal bridge before starting it, then verify exactly those two attachments. The relay exposes no CONNECT, URL-target or client-selected-upstream interface: every incoming byte goes only to its one configured tuple. It does no DNS lookup, HTTP parsing, redirects, header rewriting or byte-content logging.

Use read-only relay source/config mounts and root filesystem, no extra capabilities, no privilege escalation, forwarding sysctls disabled in the relay namespace, and a bounded tmpfs over `/data` to avoid the original image's anonymous data-volume side effect. Disable the relay's inherited app healthcheck. These are proposed container settings, not host firewall/daemon changes. Stop if exact ownership, network role, mount, forwarding or loopback-publication checks fail. An ordinary ingress interface can route externally, but the reviewed relay process can connect only to its fixed upstream; it is not an IP-forwarding gateway. Internal peer/host-bridge access still exists as disclosed by Docker; no universal hostile-host isolation is claimed.

Transparent bidirectional copying must preserve binary data, backpressure and half-close behavior, including bytes after an HTTP WebSocket upgrade. No protocol interpretation or app response is fabricated. A socket/byte limit or deadline closes the owned pair and marks the probe unresolved; it cannot silently change destination or pass a truncated transport result.

## Small no-browser admission first

The [machine contract](probe-contract.json) permits one app, one relay and two owned networks; no browser, restart, recreation or alternate topology. Reuse the existing lifecycle owners and selected preassert receipts, extended only for app IPv4 and relay attachments/publication/flags. Preserve actual selected operands before assertions. App runtime publication is intentionally absent in this topology; only the relay publication supplies the owned host origin.

After exact relay publication admission, allow at most ten GETs of `/api/health` to that one loopback origin, with at least three seconds between starts, a two-second request limit and a thirty-second readiness window further bounded by remaining input time. Stop immediately on 200; reject every 3xx or Location transition without following it. Non-200/transport readiness observations may use the remaining finite slots on the same instances. A 200 cannot pass admission if relay security/limit counters or cleanup proof fail. This differs from the consumed operand diagnostic's single GET ceiling and therefore needs its own review/grant. Retain only statuses/fixed reasons, never headers/body. No browser login, fixture or Legend action is part of the probe.

The probe relay permits at most four concurrent pairs, sixteen accepted pairs, nine process sockets including its listener, two 64-KiB buffers per pair, 4 MiB/pair and 32 MiB aggregate forwarded bytes in both directions. Pause accepting at capacity; bound every connect by two seconds. Input/cleanup/hard ceilings are 90/60/150 seconds. Existing prospective output bounds remain 32 files/2 MiB, 64 KiB/public JSON and 512 KiB/public JSON total. Use the previous conservative watchdog margins. No deadline or cap grows on failure.

Cleanup closes the relay listener/pairs and removes the exact owned relay, then app, then both empty owned networks; state and credential deletion remains inside the recorded attempt prefix. Prove IDs/names/labels before mutation and verify absence afterward. No global process/network/volume cleanup is allowed. Unexpected resources or incomplete proof remain cleanup-unverified. Store only fixed relay reasons/counters/byte totals, selected owned identities and source/config hashes; raw credential/runtime metadata stays private.
