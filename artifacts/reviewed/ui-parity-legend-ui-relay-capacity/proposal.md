## Size evidence and the proposed ceiling

[Measurements](measurements.json) use a retained candidate frontend build table and pinned original public-asset Git sizes. The candidate table has 320 outputs totaling approximately 31,997,430 bytes, with a largest reported chunk of approximately 7,915,720 bytes. The original `terminalpro/public` tree has 133 files totaling exactly 25,473,168 Git blob bytes. Candidate build output is not the original image, and printed kB sizes are rounded. Neither source measures compressed wire transfer, selected assets, HTTP headers, request count, connection reuse or WebSocket traffic in this image. No compression benefit is assumed.

For an explicitly conservative scale envelope, add five bytes per printed build row for rounding, then add the entire pinned public tree: E = 57,472,198 bytes. This intentionally includes assets the finite fixture may never request and may double-count copied/imported assets. It is a sizing assumption, not a proven upper bound on the image. Two complete banks plus 16 MiB reserve fit below 128 MiB; four banks plus 32 MiB reserve fit below 256 MiB. The existing probe's 4-MiB pair cap is below the largest retained candidate chunk, so its 4/16/32-MiB profile must not be carried into the browser journey unchanged.

| Transport operand | Proposed full UI cap | Rationale and stopping rule |
| --- | --- | --- |
| Simultaneous pairs / relay TCP sockets | 16 / 33 including listener | Headroom for parallel asset/API connections and long-lived upgraded connections. Pause listener admission at capacity. This is a proposed concurrency ceiling, not measured browser demand. Existing four-second route/action timeouts stay unchanged. |
| Lifetime accepted pairs | 4,096 | Four complete 453-object banks imply 1,812 pairs even if every object takes a fresh connection. Reserving one further new pair/second across the 2,100-second input ceiling gives 3,912; round to 4,096. The extra rate is an engineering allowance, not an observed polling rate or extra action permission. Reuse may reduce demand; it is not assumed for the cap. |
| Per-direction queued payload | 65,536 bytes | Keep reviewed backpressure behavior; 16 × 2 buffers gives at most 2 MiB user-space queued payload. Kernel buffers and Python overhead are separate and unmeasured. |
| One pair, both directions | 128 MiB | Two scale-envelope banks plus 16 MiB request/API/upgrade allowance fit. A persistent pair may carry several responses; the cap is not an individual asset limit. |
| Entire relay, both directions | 256 MiB | Four scale-envelope banks plus 32 MiB reserve fit with 4,992,232 bytes remaining. This is transferred transport data, not retained evidence or permission to download arbitrary content. |
| Connect timeout | 2 seconds | Keep the reviewed fixed internal destination timeout. No retries, alternate address or longer timeout after failure. |
| Pair/process lifetime | Existing input/cleanup clocks | No short idle or per-message timeout. Upgraded/idle connections may live through the journey. Stop browser input by 2,100 seconds, close the owned context/browser, then relay/app within the existing 120-second cleanup and 2,220-second hard ceiling. Reserve byte capacity before queueing, including both directions, and retain the repaired partial-write/half-close/EAGAIN handling. A reached pair cap, byte breach, connect timeout, truncated stream or missing/invalid counters stops unresolved; preserve the actual prefix and leave dependent cases not run. Never rerun, increase caps or replace the renderer within an attempt. Sixteen-pair saturation causing route timeout also disproves adequacy; do not hide it by lengthening browser timeouts. A profile may fail safely and require a separately justified proposal; it does not guarantee eight cases will finish.
