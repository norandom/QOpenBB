## Blocking findings

1. **Critical: a combined read/write event can silently discard unread bytes.** In [relay.py](../ui-parity-legend-fixed-relay/harness/relay.py), `transfer` at line 149 reads before writing; the `BlockingIOError`/`InterruptedError` handler at line 171 skips `refresh`. If the read fills the opposite-direction buffer and the subsequent send returns EAGAIN, the previous read interest remains registered. The next readable event calls `recv(0)` at line 131, which is interpreted as EOF even though peer bytes remain. The [injected-socket reproduction](counterexample.py) forwards 65,544 bytes, leaves one client byte unread, closes the pair and retains zero violations. Both received and forwarded counters agree, so equality alone cannot detect this loss. This violates the plan's opaque-byte, backpressure and half-close contract and its prohibition on passing truncated transport.

   Required fix: reconcile selector interest after every successful state change, including when a later operation would block or is interrupted; never infer peer EOF from a zero-capacity receive. Add a focused combined READ|WRITE regression that fills the opposite buffer, injects send EAGAIN, drains the buffer and proves the remaining byte is forwarded without premature half-close. Keep the existing fixed-destination and byte/socket limits.

2. **Critical: expected-name absence can be reported as recorded-ID absence.** In [cleanup.mjs](../ui-parity-legend-fixed-relay/harness/cleanup.mjs), `cleanupOwned` lines 24-33 queries expected names before removal and again for absence. When those lookups are empty, it never queries the already recorded container IDs. The [injected control reproduction](counterexamples.mjs) keeps both recorded IDs present under renamed names, detached from the two owned networks. The expected-name searches return none, empty owned networks are removed by the fake driver, and `absenceComplete` returns true while both recorded IDs remain. This is an identity-drift failure, not a demand to delete arbitrary renamed resources. The approved plan requires exact ownership checks before mutation and actual owned-resource absence afterward; unexpected resources must remain unverified.

   Required fix: make recorded IDs authoritative for absence checks when available. Check expected name/ID/label relationships before mutation, and return cleanup-unverified for a surviving ID or mismatch. Preserve the finite, exact name-plus-label recovery for partial creation when an ID was not recorded. Add this drift case and an exact-ID post-removal survivor case. Do not expand cleanup into global scans or deletion of unknown resources.

3. **Important: new relay admission flags are reduced to assertions before their selected operands are saved.** In [admission.mjs](../ui-parity-legend-fixed-relay/harness/admission.mjs), `networkProjection` at line 13 and the new relay security projection beginning at line 24 persist comparison booleans for fields such as Internal, forwarding sysctls, read-only root, healthcheck, capability drop and mount flags. The control reproduction demonstrates that an explicitly false Internal value and an absent Internal field produce identical saved receipts. Newly proposed flags can therefore fail without preserving the bounded operand shape/value needed to interpret that failure. Port and state projection is more informative, but does not repair the new flags' evidence gap. The plan specifically says to preserve actual selected operands before stopping assertions.

   Required fix: add narrow, bounded nonsecret projections for the selected network flags and new relay admission fields, including missing/type/value distinctions, and persist them before evaluation. Keep ownership-label values private: equality booleans for ownership tokens are intentional and need not change. Do not publish raw inspect, environment, credential arguments, arbitrary error strings or complete configuration. Add focused missing-versus-false/mismatched-flag checks and secret-exclusion checks. Reusing older ownership comparison helpers does not waive the new plan's actual-operand obligation.
