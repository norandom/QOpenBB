# H3 hierarchy application integration plan

**Design independently approved; implementation waits for H2 acceptance.** This is a serial integration plan against accepted H1c and H2 declarations at Workspace `fc0f02f`, pending independent acceptance of the two H2 implementation lanes. It introduces no production edits. The controller owns commit boundaries, inventory, heavy-check scheduling and final review. H4 browser comparison remains separate.

All production paths below are relative to `vendor/workspace/terminalpro/src/components/General/Table/Chart/`. Preserve other workers' changes. Do not edit H1 capture/preparation or H2 renderer/controls except through an explicit reviewed finding. Parent-approved H2 helper additions `application/hierarchyAppearanceValues.ts` and `echarts/hierarchyLabels.ts` remain H2-owned.

## What the actual join requires

The existing application has one transaction/session owner, but its `ApplicationSessionState.capture`, commit and context assume scalar `ChartSnapshot`. `captureApplicationSession` reads ordinary `sessionSetup`; `contextFor` assumes any retained capture is ordinary. Initialization/synchronization create fake capture casts even for capture-free range/baseline reads. The hierarchy branch must be admitted before these assumptions, not cast through them.

`ChartSetupPanel` supports one category and emits `ChartSetupEdit`; hierarchy needs ordered category add/remove/reorder and zero to two numeric fields. `ApplicationCustomizeEditor` treats every axis-free state as a categorical legend owner, and `ApplicationSeriesEditor` then treats remaining axis-free state as Pie. Both need explicit hierarchy handling before those fallbacks. `AgChartView` currently excludes hierarchy from the live-family route and disables ordinary zero-series charts; hierarchy deliberately permits no Size. Its no-data overlay must not be extended to hierarchy: all-zero original plots remain blank.

`useApplicationChartSession` combines family projection, grid recapture dispatch and host/callback mapping near its cap. `lifecycle.ts` is also near its cap. Extract cohesive owners before adding branches, retaining existing behavior and tests. Do not solve limits by hiding statements or adding an unbounded generic dispatcher framework.

## Capture, recapture and transactions

Hierarchy capture branches before ordinary `sessionSetup` or `categoryColumnId` reads. Use H1 `captureDisplayedHierarchy` with ordered categoryColumnIds, all required numeric descriptors, current public grid range/stamp and detached original model. Zero categories and zero series are valid. Filter out the ordinary DEFAULT_SETUP_CATEGORY descriptor from hierarchy selection/choices; never display or capture a synthetic '(None)' hierarchy level. Capture includes selected category IDs plus the union of current/retained/required numeric IDs, preserving H1 transition.recapture requirements. Do not run ordinary `retainOrdinarySetupCapture` on hierarchy.

The hierarchy selection is validated from saved range and model using the exact range rules below. Do not truncate an accepted H1c selection inside preparation. Preserve row bounds and originalRange unknown fields. No-series availability must not make an already active hierarchy chart disappear.

### Hierarchy range resolution and initial numeric selection

`application/hierarchyRange.ts` is the single pure owner shared by `caller/chartInputs.ts` and `application/applicationSessionRange.ts`; ordinary `resolveChartRange` is unchanged. Export `resolveHierarchyRange(input: HierarchyRangeInput): RangeResolutionResult`. `HierarchyRangeInput` has readonly `storedRange?:ResolvedRange`, `ignoreCellRange:boolean`, `configuredColumnIds?:readonly string[]`, `generatedColumnIds:readonly string[]`, `columns:readonly SnapshotColumn[]`, and `numericCollectionIds:readonly string[]`. These are data inputs, not GridApi. Both pure range exports return the existing unstamped `RangeResolutionResult` from `application/types.ts`; the session caller adds its checked stamp to a session envelope later. Numeric collection order is supplied by the caller from public `api.getColumns()` order, restricted to admitted numeric descriptors; absent/unready API defers live capture rather than asserting displayed order equivalent to the original collection order. Before API readiness a provisional definition-order input may project caller metadata only, but the live session dataKey must change to the public order and recapture before acceptance. Transport `numericCollectionIds` in rangePolicy (and thus its existing dataKey) so session and caller use the same order.

Selection algorithm:

1. Validate unique known IDs, ordered finite row bounds and detached data-only originalRange. `storedRange !== undefined`, rather than its length, establishes an explicit saved selection when `ignoreCellRange` is false. Preserve `[]`, `[Region]`, `[Size]`, category order and numeric order. Intersect retained IDs with currently generated eligible columns as the existing visibility contract requires, but do not refill an empty result. Validate the explicit saved numeric count before this intersection: more than two is invalid, even if hidden columns would reduce it. Retain row bounds and all unknown originalRange members; projected originalRange.columns reflects the effective selected vector without mutating storage.
2. If there is no applicable stored range, use configured IDs that match admitted descriptors. Preserve their supplied order as the candidate selection. As in existing configuration precedence, an empty/no-matching configuration falls back to generated IDs; this differs intentionally from an explicit saved empty range. Intersect with generated eligible IDs. An empty intersection is a valid empty hierarchy range, not ordinary `empty-generated-intersection` failure. Initial generated/configuration candidates may contain more than two numbers and pass through the membership/order rule below.
3. For initial generated/configuration candidates only, walk `numericCollectionIds` in public column collection order, select the first at most two numeric IDs present in that candidate and generated eligibility set, then sort those selected IDs by candidate range order. Preserve candidate category order. Reconstruct columns as ordered categories followed by the selected numeric order, matching hierarchy's dimension/value ranges. This separates numeric membership from Size/Color assignment. Example: public numeric collection `[A,B,C]`, configured candidate `[Region,C,B,A]` selects members A/B, then assigns Size=B and Color=A; simply slicing C/B would be wrong. No candidate numeric IDs means no-size equal-count, not a fallback to a number.
4. Fresh initialization with ignoreCellRange=true ignores the stored range and follows configuration/generated precedence. A currently accepted local Setup range with matching rangeFrameKey retains its explicit selection (including empty) under the existing same-frame rule; pass it as the effective storedRange with ignoreCellRange=false. After external range/configuration identity changes the local override expires. Both caller and session call this owner, so fresh reopen without a rangeFrameKey still preserves applicable saved empty/single-column ranges.

Source basis: pinned AG Grid34.1.1 G42894 constructs numeric `valueCols` in column-model collection order; G43363–43388 chooses at most two eligible in-range values in that order and only then sorts selected values by prior value-state or supplied-range order. This plan's initial path has no prior value-state and therefore uses supplied candidate order. Existing hierarchy saved vectors and Setup ordering are already explicit state and are never normalized by that initial path. No H1 type/reducer changes are needed.

### Gallery entry numeric rule

The existing `familyTransition.ts` owner calls a second pure `hierarchyRange.ts` export, `normalizeHierarchyGalleryRange(range, columns, numericStateOrder, previousFamily):RangeResolutionResult`, before committing a target Treemap/Sunburst family. `numericStateOrder` is selected numeric IDs in the current retained range order followed by unselected eligible IDs in public collection order; it represents the existing ordered value-column state without adding a second stored assignment list. Discard ordinary `DEFAULT_SETUP_CATEGORY` from the actual selected range as well as descriptor choices before hierarchy gallery normalization; it is not a hierarchy category. Preserve the remaining ordered categories, row bounds and unknown originalRange members.

Pinned G45782–45809 trims selected value state only when the old maximum exceeds the target maximum2. For currently supported source families, G41531–41543 gives previous maximum1 for pie/waterfall/histogram,2 for Treemap/Sunburst and unbounded for the remaining supported families. On reduction from unbounded to2, retain the first two selected numeric IDs in numericStateOrder. If zero were selected in that reduction branch, select the first eligible entry in numericStateOrder, matching original updateForMax's first-entry fallback; if no numeric descriptor exists, retain empty rather than dereferencing an absent entry. This fallback is limited to that gallery reduction event. It never runs on saved hierarchy reopen, explicit no-size Setup, Treemap↔Sunburst or a previous maximum1→2 transition. Those paths preserve deliberate zero selections. Nonreduction state with more than two selected values is invalid rather than silently normalized.

Persist the normalized gallery range atomically with the target model using existing range transition ownership, then clear retained capture for the new family. Retain inactive options. The common commit capture becomes optional for family changes, and execute-command must branch on its presence rather than spreading undefined into a fake capture. Subsequent public capture uses the new category/numeric vector. This is separate from malformed saved hierarchy input: an already saved explicit hierarchy range with three numeric IDs remains invalid.

Focused amendments to the existing planned test owners: caller and fresh-session initialization/reopen-equivalent `[]`, `[Region]` and `[Size]`; ignoreCellRange/configuration precedence; ordinary resolver regression unchanged; reversed configured three-number membership versus role order; explicit saved three-number rejection; ordinary three-number gallery entry retaining first two state entries; and zero-selection fallback only in the maximum-reduction gallery branch. These are boundary cases, not a new resolver framework or repeated financial reducer matrix.

`applicationSessionRecapture.ts` extracts capture-before-reducer dispatch planning from the hook. For hierarchy Setup, evaluate the pure H1 transition to identify requested category order/columns, then read the public grid outside `owner.transact`. Inside the latest Widget transaction, rerun selection/transition from current state and verify the proposed recapture still matches it. Do not read grid APIs in replayable reducers.

Hierarchy Setup transaction order:

1. Admit immediate commands with `validateSynchronousEditorStamp`: validate the complete stamp shape and require current address/generation/data identity, while allowing an intervening option-only render revision. Check current family, latest Widget range inputs and assignment/data identity. Compare current baseline-derived setup/range against command frame. Do not require current arithmetic projection to succeed: overflow must remain recoverable by aggregation-off/removal. A previous Setup commit advances data revision and therefore still invalidates commands from the old data frame.
2. Call `transitionHierarchySetup` using validated capture/selection/model. If recapture requested, require a ready result and validate its complete stamp exactly against the original command stamp with `validateSessionStamp`; then require current address/generation/data freshness through `validateSynchronousEditorStamp`. Check capture stateAddress/dataRevision, exact ordered category IDs and every requested/retained numeric descriptor against the freshly rerun transition. Raw capture is independent of an option-only redraw, so a render-only advance cannot invalidate matching origin provenance. An origin mismatch, changed data/generation/family, partial, wrong-kind or wrong-category recapture writes nothing.
3. Run `projectHierarchySetup` on the prospective capture/selection before persistence, including zero-series and no-category cases. Invalid finite arithmetic writes nothing. No second aggregation or missing-value transform.
4. Replace the full chartModel where necessary so aggregation-off actually removes aggFunc; use existing `reduceSessionOptions` and `applyRangeTransition` ownership for original paths/partition persistence. Preserve unknown and inactive model fields, row bounds, inactive aggFunc with no categories, and unrelated storage. Do not set categorical legendEnabled from series count.
5. Commit storage/local/capture together through existing execute-command return; advance data revision once and retain matching capture.dataRevision. Appearance edits advance render only. H1 output remains detached. No half-applied category/range/model state escapes.

Hierarchy appearance transactions use the same immediate-command stamp admission, check current family/baseline/range/setup/capture, derive current style/assignments, map exactly one intent and use the existing reducer. Consecutive immediate edits from one rendered panel must compose against latest storage after the first advances only render revision. Font context comes from the new selection; no captured UI style enters storage. Invalid/disabled-gradient/stale intents preserve Widget identity. Count/no-size/missing policy is unchanged. Export, renderer and hover freshness retain exact revision checks; the immediate-control allowance does not apply to asynchronous actions.

Required stamp regressions: two appearance intents with one originating stamp both persist against successive current baselines; changed address/generation/data or family is rejected; malformed stamps are rejected; recapture whose stamp differs from its originating command is rejected; matching-origin recapture remains admissible after an option-only advance when the freshly rerun transition still matches; changed category/required numeric descriptors remain rejected. Keep these in the existing H3 session test owners.

Runtime synchronization compares hierarchy setup via `selectHierarchySetup` instead of scalar `sessionSetup`, and includes capture policy change between ordinary and hierarchy in invalidation. Add hierarchy palette to appearanceKey and retained appearance copies. Skip axis persistence/rebuild and categorical legend toggles for hierarchy. `notifyChartUpdate` likewise avoids scalar setup/legend side writes. Family changes invalidate capture before rendering the new family, including Treemap↔Sunburst and hierarchy↔ordinary; do not reuse old kind under a new tag.

Gallery uses existing family transition persistence. Make its capture-independent helpers accept frame/common-envelope types and retain numeric checks; do not cast hierarchy into Combo context. Entering Combo from hierarchy uses existing assignment resolution with common descriptors, then clears capture for ordinary recapture. Leaving hierarchy retains unknown inactive options and uses existing axis-reset behavior. Tests must cover one switch in each direction and Treemap↔Sunburst, not every family pair.
