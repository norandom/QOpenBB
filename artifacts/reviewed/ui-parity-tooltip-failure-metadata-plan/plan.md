# Bound failure metadata before reconsidering the reservation proof

Propose a local serialized failure-metadata policy for the existing case and outer catches. Keep the 32,768-byte input reservation, 115,072-byte guard, 16,000-byte final tail and 131,072-byte case ceiling unchanged. This proposal selects no smaller reservation and makes no complete-terminal-record guarantee. It requires independent review before implementation; no collector edit or runtime is authorized here.

The [reservation review](../ui-parity-tooltip-reservation-review/review.md) establishes the prerequisite: actual catches retain arbitrarily large first-line text outside bounded ledger entries, so a nominal 2,048-byte scaffold cannot prove a finite append interval. Inputs are pinned in [source-hashes.json](source-hashes.json). The owning language is English and the audience is engineers assessing evidence completeness, not a logging-system design.

## Smallest policy for the actual catches

Use one local pure formatter shared by the two catches in [journey.mjs](../ui-parity-tooltip-segment-keyboard-revised/harness/journey.mjs), currently lines 122-125 and 131-135. It returns only four fields: `reason`, `reasonCode`, `reasonOmitted`, `failureOrigin`. Its whole JSON object, including keys and punctuation, must serialize to at most **512 UTF-8 bytes** using the existing `Buffer.byteLength(JSON.stringify(value))` rule. This is a new proposed metadata ceiling, not a reduction of any existing allowance. Character counts are insufficient.

Read `error.message` once inside a guarded extraction. Accept only a string; do not enumerate the thrown object, serialize a stack/cause graph or invoke an arbitrary nonstring `toString`. Preserve the source's exact `message === 'not-run-budget'` classification before redaction. Apply the existing exact nonempty synthetic email/password substitutions to the message. Retain the complete redacted message, including newlines, only if the complete four-field object fits. Do not retain an unexplained first-line or character truncation.

| Outcome | `reason` | `reasonCode` | `reasonOmitted` |
| --- | --- | --- | --- |
| Complete redacted message fits | Complete redacted message | `not-run-budget` for that exact source sentinel; otherwise `exception` | false |
| Full metadata would exceed 512 bytes | `Failure message omitted: serialized metadata limit` | `message-over-byte-cap` | true |
| Message extraction throws or is not a string | `Failure message unavailable` | `message-unavailable` | true |

`failureOrigin` is exactly `case` or `outer`; it is never derived from exception text. An empty string is a complete message and may be retained. `reasonOmitted: false` means the complete redacted message was retained; it does not claim a full stack, cause, unredacted secret or financial observation was retained. An omitted message is not a known cause. No arbitrary original-byte-count field, hash of secret-bearing text, external log file or variable-length diagnostic history is added. Fixed fallback objects must themselves satisfy the 512-byte cap, verified before adoption.

The byte measurement and fallback selection occur **before assignment** to case/preflight/failure state. The formatter must not throw merely because text is too large. Redaction or extraction failure chooses the fixed unavailable form. The policy bounds retained serialization; it does not claim bounded memory allocation for an already materialized exception message or a hostile message getter.

## Retain the first case failure and distinguish closing failure

The case catch keeps its existing `not-run-budget` versus `unresolved` status decision. Assign the bounded fields to the case at the existing reason location. Remaining-probe records keep their exact target and status, but use the fixed reason `Affected case closed; see case reason` instead of concatenating the message for each target. Remaining-mode status and mode identity stay unchanged. For T06, `remainingProbes` is empty; the shared catch still needs the fixed reason rule for the other seven cases.

The outer catch keeps `process.exitCode = 1` and the existing case/preflight unresolved status. If a case already has case-origin metadata, preserve it and retain at most one bounded `outerFailure` object for the closing error. Otherwise assign outer-origin metadata at the original reason location. Do not replace the first failure with `Case JSON bound` and lose its provenance. At most two bounded objects belong to a case: one first failure and one closing failure, not an append-only history. The `outerFailure` property name/braces/comma and status changes are additional scaffold bytes, not included in the two 512-byte caps.

The separate existing failure receipt uses that same bounded outer metadata, fixed phase/case identity and the existing bounded completed-case list. It must distinguish `caseWrite: succeeded`, `caseWrite: rejected-prior-prefix`, or `caseWrite: not-attempted` from the actual persistence result; do not infer write success from the in-memory object. This finite three-value field is proposed terminal evidence, not permission for another input or retry. If a closing write itself fails, do not recursively log that exception or attempt an unbounded fallback chain. The hard writer remains authoritative, and even a standalone failure receipt can be rejected by the aggregate byte limits.

Actions and probes already counted stay counted. A `started` input persisted before dispatch must not be rewritten as never attempted; a dispatched input with failed observation must not become observed or be removed. If a failed `input()` has already left an oversized entry in memory, bounding case/outer reasons does not legalize that entry. Keep the accepted physical prefix when the writer rejects the complete object and report the terminal-write outcome if its bounded receipt fits. Do not delete the entry, decrease counters, strip tooltip/financial values or fabricate a complete final case merely to fit. Any proposed improvement to that input path needs its own narrow source correction and proof; this proposal does not hide the remaining obligation.

## Finite scaffold proof required before any reservation decision

The formatter would remove one unbounded text source; it does not enforce the previously assumed 2,048-byte scaffold. Derive the whole interval from the exact journey source: immediately before each `reserveInput(current)` through the next reservation or case close, including all throwing exits. The [retention functions](../ui-parity-tooltip-segment-keyboard-revised/harness/keyboard-retention.mjs) and [writer](../ui-parity-tooltip-segment-keyboard-revised/harness/io.mjs) remain separate enforcement layers.

| Interval contribution | Required proof |
| --- | --- |
| Started/completed input entry and counters | Include object/array punctuation, counter digit growth, eventsFrom/eventsTo, status/time replacements, successful after-data and failed reason. Validate the actual 6,144-byte entry rule; distinguish a rejected mutated entry from an accepted finite one. |
| Control receipts and mode/baseline creation | Count the maximum source-permitted additions between checks, not a guessed multiplicity. Include the 1,024-byte control objects, 2,048-byte baseline object, first property key, mode wrapper, array separators and failure after baseline assignment. |
| Tab/arrow invocation and image references | Include the 14,336-byte invocation object, enclosing comma, mode status, initial/terminal image properties, existing before-image reuse and screenshot failure before a reference is assigned. Keep actual unresolved sample pairs unchanged. |
| Case close | Include status replacement, bounded case metadata, fixed remaining-probe reasons, target tuples, remaining-mode wrappers and all commas/keys. Test both empty T06 probes and maximum applicable nonkeyboard targets. |
| Outer close after earlier failure | Include the maximum second metadata object, its wrapper, preservation of the first reason, write-result enum and the standalone failure receipt separately. Challenge both the attempted full write and the prior-prefix-preserving replacement path. |

Measure exact serialized deltas between snapshots, including replacements that grow rather than append. Derive finite lengths/cardinalities from the fixed [contract](../ui-parity-tooltip-segment-keyboard-revised/harness/contract.mjs); any varying field not covered by a source cap or explicit finite validation remains a proof gap. Precompute or enforce the proposed scaffold before committing its mutations; a failed post-write assertion is not prospective enforcement. Do not introduce a generic state walker or log framework to replace the named owners.

The proof must establish that the complete pre-tail candidate is at most 115,072 bytes whenever it claims terminal fit. Validate the unchanged final `{events, elapsedMs}` object at 16,000 bytes separately before merging. For disjoint keys merged into a nonempty object, the recorded merge delta is tail bytes minus one; overlapping/replacement cases need their own exact calculation. The hard case ceiling is 131,072 bytes. Global JSON/run limits and their reserved output allowance are independent; they cannot be borrowed as case headroom. Checked writer rejection preserves the previous file, but this is not a filesystem-crash atomicity claim or proof that the prior file remains final after a later successful bounded write.

## Required offline disproof tests for an implementation proposal

Execute the actual revised catch/input/keyboard/writer functions under mocks, not only a formatter look-alike. Required faults are complete messages immediately below/at/above the metadata byte boundary; quotes, slashes, newlines, NUL escapes, multibyte text and unpaired surrogates; empty/nonstring/throwing message access; credential redaction; and the exact `not-run-budget` classification. Assert no altered financial, identity or tooltip value and explicit omission whenever the message is unavailable or excluded.

Repeat the established 6,000-character input, 27,624-character case, 40,000-character outer and 7,000-control-character counterexamples. Inject after counted input, during observation, after baseline assignment, at screenshot failure, during tail collection and during final persistence. Retain the first failure when a second closing error occurs. Verify both the in-memory attempted record and actual prior/final file hashes; an oversized completed object must never be claimed written. A legal maximum tail must not silently disappear from a claimed complete case. Invalid component objects that cannot produce a complete case must instead produce an explicit unresolved/prefix outcome, without a claim of universal complete retention.

The independent reviewer must reject any scaffold bound lacking an actual append path, or any accepted component state whose intervening growth exceeds the declared interval. Synthetic API-admissible boundary objects and demonstrably runtime-reachable states must remain labelled separately. The historical 70-Tab stop and unfinished 72-Tab coverage remain unchanged evidence; this proposal does not predict improved keyboard capacity.

## Review and delivery boundary

Implementation ownership, if later approved, would be limited to the two actual catches and their local formatter/retention responsibility, fixed remaining-probe text, corresponding source-only faults and manifests. No runtime/network/lifecycle repair, fixture change, collector constant change, new screenshot or application behavior belongs to this proposal. A further change to input rejection behavior must be explicit rather than smuggled into the metadata helper.

This package contains only this proposal, pinned source references and a read-only verification receipt. No production code, frozen research input or Git state was changed; no calculator, collector, browser, container, provider request, build, installation or runtime ran. The proposal is not implemented, and no scaffold proof is claimed complete. Traffic-denial/lifecycle prerequisites, T04/T05, picked identity, full keyboard reachability and UI parity remain open. Research artifacts are excluded from production size caps; future maintained adoption retains the inventory/checker foundation, 400 physical lines/file, 300 logical units/file, 50/function and independent review.
