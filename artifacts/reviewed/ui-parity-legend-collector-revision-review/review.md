## B01 remains open only for continued HTTP redirects

[routes.mjs](../ui-parity-legend-capture-revised/harness/routes.mjs), line 8, approves the first generic request origin and calls `route.continue()`. Line 11 does the same for non-GET sync requests. Only sync GET uses no-follow fetch and checks its response. Thus an allowed `/login` GET or same-origin POST that responds with an external `Location` can cause Chromium to contact that external origin without another `allowed()` check.

This follows from the installed Playwright 1.64.0 source, not an assumed API behavior. Its `coreBundle.js` at line 37601 detects `redirectedFrom`, sends `Fetch.continueRequest`, and creates no route for that hop; the code serves both page and context requests. The verification receipt hashes this local file and records its exact location. The [official route documentation](https://playwright.dev/docs/api/class-page#page-route) states that the handler applies to the first URL in a redirect chain; the [Chromium implementation](https://raw.githubusercontent.com/microsoft/playwright/main/packages/playwright-core/src/server/chromium/crNetworkManager.ts) exposes the shared continuation branch. The independent mock check confirms both collector paths choose unrestricted continue. No browser or network redirect was executed.

Smallest correction: use bounded no-follow fetching for every approved HTTP(S) request, including generic GET and non-GET paths, while retaining the request's original method/body and response semantics. Reject redirect responses or Location transitions before fulfilling them; record a bounded traffic/admission/case-unresolved reason. Do not emulate redirect chains, invent an application response, change origins or rebuild the UI. Ordinary nonredirect responses should pass through with their status, headers and body. Keep the existing four-second request timeout and no retries. Add offline faults for generic GET, POST/non-GET, redirect status, foreign response identity and ordinary nonredirect passthrough. An original application redirect may then stop the one future attempt; it is not permission to relax denial.

The other B01 changes are adequate source corrections. All specialized callbacks reject external initial URLs independently; routing is context-wide; service workers are blocked; sync GET prevents automatic redirects. The backend now receives one owned internal bridge, checked network identity/label/driver/Internal/IPv6 values, exclusive container attachment, loopback DNS, empty proxy settings and a single inspected loopback publication. Startup rejects health redirects. Cleanup checks ownership, removes the owned container before its empty network and verifies absence. Partial creation uses the prewritten ownership receipt and exact labels rather than a global cleanup.

Docker's [internal-network documentation](https://docs.docker.com/reference/cli/docker/network/create/#network-internal-mode---internal) supports external-network isolation while expressly retaining host-gateway access. That disclosed residual is not a new blocker for this finite synthetic setup with no configured relay/provider endpoint. Actual internal-network creation and loopback port viability remain future admission checks, with no fallback topology. The backend bridge does not isolate the host Chromium process and therefore does not close the browser redirect defect above.
