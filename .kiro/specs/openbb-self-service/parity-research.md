# Renderer compatibility research

Strict OpenBB parity is not yet demonstrated. Perspective 5.6.0 provides useful computation, configuration and export seams, but does not implement the AG Grid Enterprise or Highcharts application contracts. Proceed to bounded feasibility probes before approving renderer remediation. The selected library does not authorize a new interface, a smaller configuration language, changed flags or unavailable legacy widgets.

Research date: 2026-10-16. This report contains source inspection and primary-documentation findings only. No browser, build, dependency installation or runtime parity test ran for this research. Earlier isolated Perspective tests remain evidence of their recorded scope, not integrated parity.

## Concrete public seams

The installed 5.6 viewer exposes `load(Client | Table | Promise<...>)`, `restore(ViewerConfigUpdate)`, `save`, `getView`, `getSelection`, `setSelection`, `resize`, `restyleElement`, `flush` and `delete`. Configuration exposes columns, grouping, splits, aggregates, expressions, filtering and sorting, plus plugin-specific settings. The client View exposes windowed `to_json`, `to_columns`, `to_csv`, `expand`, `collapse` and `set_depth`. These permit existing OpenBB controls to drive an analytical engine without adopting native Perspective controls. Public signatures do not demonstrate identical event timing, data ordering, formatting or gestures. See the [viewer API](https://perspective-dev.github.io/viewer/classes/dist_wasm_perspective-viewer.d.ts.PerspectiveViewerElement.html) and [pivot example](https://perspective-dev.github.io/guide/use_cases/streaming_pivot_table.html); online documentation is not an immutable 5.6 contract.

`getSelection` returns a `ViewWindow` for a selected region; `setSelection` accepts one window. This is not evidence of AG Grid's multiple disjoint cell ranges, pinned-row coordinates, header selection, drag gestures or keyboard semantics. A chart click filter is also not equivalent to a rectangular selection. Keep selection semantics in an application-owned interface and prove each original gesture.

The 5.6 configuration declares `settings` as cosmetic sidebar visibility. Closing it does not prove that all native viewer chrome can be removed or that its grid looks like OpenBB. Theme names and opaque plugin settings are not a generic AG theme compatibility API. If public plugin/configuration APIs cannot supply the original surface, a custom rendering surface using Perspective Views is an architectural option requiring a measured probe, not permission to patch private shadow-DOM internals.

## Compatibility components to evaluate

These are proposed responsibilities, not implemented interfaces. Keep original widget IDs, endpoint handling, parameter controls, dashboard framing and feature-flag predicates as the contract. Do not introduce a second dashboard or new product controls.

| Component | Responsibility and boundary | Decisive limitation |
| --- | --- | --- |
| Legacy state codec | Read existing grid/chart/formula/theme storage into validated application state; preserve original fields and unknown payloads; emit compatible saved state | A saved Perspective token cannot replace AG chart models or erase unknown legacy fields |
| View coordinator | Own dataset revision, displayed order, aggregation/filter state and cancellation; translate supported operations to Perspective Views | A pivot result is not necessarily equivalent to AG grouping; preserve null/date/unit/currency and aggregate semantics |
| Grid surface adapter | Existing Community grid for proven flat paths, or a custom surface driven by a Perspective View where necessary; preserve original column cells and controls | Community does not gain Enterprise modules when fed aggregated rows; group hierarchy, generated columns and menus still need compatibility work |
| Selection service | Capture ordered column IDs, stable row identities/group paths, ranges and data/view revisions; expose the same snapshot to copy, chart and Copilot | Visible indexes become stale after sort, pivot or refresh; multiple ranges may need independent interaction/rendering support |
| Existing action bridge | Wire original menus, sidebar controls, stats, formulas, keyboard and header actions to typed operations | Reimplementing vendor-supplied panels is substantial UI compatibility work even when OpenBB wrappers survive |
| Chart model adapter | Preserve original chart model/storage and chart-to-widget flow; dispatch enumerated chart families to proven renderers | Avoid exposing vendor objects as a counterfeit complete AG Grid API; finite adapters do not emulate arbitrary options |
| Export service | Export the same revision/view/selection with original labels, styles and type semantics; use existing ExcelJS for an XLSX feasibility probe | CSV renamed to XLSX, unfiltered raw rows or lost formats do not satisfy the action |
| Theme adapter | Map existing OpenBB chart/font/palette/background/tooltip/legend/zoom settings to a specific renderer | Matching chart family alone does not establish visual or interaction parity |
| Remote table coordinator | Preserve existing endpoint request, paging, hierarchy, pivot result and failure behavior | Cannot treat a loaded page as the whole dataset for grouping, exports, statistics or Copilot |

Freeze typed application interfaces before parallel implementation: a revision-bearing `ViewSnapshot`, legacy-compatible state codec, selection snapshot, chart request/model, export request and cancellable remote query. Their schemas must come from the original call sites and inventory, not the reduced renderer allowlist. Capability checks are internal acceptance diagnostics; they must never silently disable original controls. Runtime failure handling remains necessary, but an unsupported-state screen is not successful parity.

## Hard gaps and plausible bounded paths

**Aggregation-policy conflict.** The [capability matrix](../../../docs/renderer-capability-matrix.md) records original `sum`, `min`, `max`, `avg`, `count`, `first` and `last` choices and default sum. A validator that removes EPS sums or other previously available operations changes this contract, even if financially motivated. Separate preserving legacy choices/results from explicitly approved validation for newly introduced ready datasets; do not apply the latter retroactively without reconciliation. This report does not approve either a silent restriction or silently changing arithmetic. The [earlier aggregation research](../../../artifacts/task-2.9/aggregation-guard-design.md) assumes native exploration and a more permissive UI policy, both superseded. Its source finding that configuration events are not cancellable, and its render-versus-export enforcement concern, remain useful evidence; its plugin-decoration proposal is not a parity acceptance path. Include original default/explicit aggregation operations in the view probe before freezing policy interfaces.

**Enterprise grid UI and analytical behavior.** Original `General/Table/hooks/useTableContext.tsx` builds the Columns/Formulas sidebar from `enableAdvanced`, `enableFormulas`, `isPivotMode` and `openedToolPanel`; formula columns use the existing expression compiler. Preserve this language and its restrictions before considering translation to Perspective expressions. Grouping/pivot results can plausibly come from Perspective, while original panels, dragging, grouping rows, statistics, advanced filters and custom cells need separate compatibility. AG's own [Community/Enterprise inventory](https://github.com/ag-grid/ag-grid) identifies the missing Enterprise modules. No examined public API restores those modules inside Community. A wrapper with identical labels is insufficient without the same working outcomes.

**Range charts and saved models.** Original `General/Table/hooks/useCreateChart.ts` reads `getChartModels`, normalizes `cellRange`, traverses filtered/sorted or server-side nodes, handles group/auto-column identity, creates `ag_chart_from_table`, and saves `chartModel` plus chart data. Its behavior cannot be restored by merely selecting a Perspective plugin. Preserve chart selection, grouping transformation, range limits, chart settings, creation into the current dashboard/tab and reopening. Start with a finite adapter for one representative model, then enumerate all accepted families and configuration fields. Existing AG Charts Community may preserve basic families with less translation, but original navigator/mini-chart/zoom functionality needs separate proof. AG documents [navigator behavior](https://www.ag-grid.com/charts/javascript/navigator/) as Enterprise; current online examples are newer than the repository's 12.1.1 pin.

**SSRM and SQL.** Original `General/Table/AgGridSSRM.tsx` uses `IServerSideGetRowsRequest`, start/end rows, grouping, pivot state, server results and explicit Copilot execution capture. A Perspective browser table holding one response cannot substitute for this protocol. Preserve remote requests and totals, or demonstrate an explicit remote coordinator that presents the same hierarchy and selection semantics. Bulk-fetching all data changes scalability and endpoint behavior and is not an assumed solution. AG documents [group requests](https://www.ag-grid.com/javascript-data-grid/server-side-model-grouping/) and [pivot result fields](https://www.ag-grid.com/javascript-data-grid/server-side-model-pivoting/). SQL and specialized financial widgets need individual data/state tracing; a common unavailable registry entry is not a replacement.

**XLSX.** Original `excelFunction` delegates to `exportDataAsExcel` with a report filename; the surrounding grid configuration may supply additional formatting and export processors. Existing ExcelJS makes workbook construction plausible, including explicit cells and styles, but the exact original export contract must first be inventoried. Verify workbook contents and types, dates, headers, grouped/filtered rows, selected scopes and any formulas/styles used by callers. [ExcelJS documentation](https://github.com/exceljs/exceljs) describes workbook APIs; [AG export customization](https://www.ag-grid.com/javascript-data-grid/excel-export-customising-content/) explains why callback/format semantics matter. No export parity is established here.

**Highcharts endpoint payloads.** Original `Widgets/charting/ChartHighcharts.tsx` accepts endpoint `userOptions` and chooses `chart`, `stockChart`, `mapChart` or `ganttChart`; it passes the options directly to the matching Highcharts constructor. Thus the input contract is not an eight-chart allowlist. Preserve raw-data toggling, query/theme parameters, refresh, AI context and builder authoring in addition to rendered output. [Highcharts' API](https://api.highcharts.com/highcharts/) and [Plotly's schema](https://plotly.com/javascript/reference/) are different option models. Existing Plotly can be evaluated for particular chart families, including hierarchical/polar/waterfall shapes, but no total translation of arbitrary Highcharts options, stock/map/Gantt behavior or extension semantics follows. A finite inventory of known payloads improves evidence but cannot silently redefine the accepted open-ended endpoint contract. This is a blocking feasibility question under the strict requirement.

## Bounded probes before implementation approval

Each probe needs an independently reviewed result with original/candidate revision, exact package identity, fixture, expected outcome and observed outcome. Proposed checks below are not completed tests. Do not start broad adapter construction before the hard probes resolve.

1. **Public surface and theme probe:** one existing table widget and one chart widget, their original controls and both themes. Drive operations only through retained OpenBB controls. Exercise headers, tooltips, fonts, sizing, legends, company background and resizing. Fail if native chrome remains, a setting is lost, or private vendor internals are required for basic continuity.
2. **Selection and action probe:** a small fixture with nulls, dates, duplicate values, sorting, hidden/reordered columns and grouped rows. Exercise original header/double-click, keyboard and disjoint-range gestures where inventoried. Compare copy, copy-with-headers, statistics, chart creation and Copilot against one revision-stamped expected snapshot. Fail on row/column identity drift or broadened selected-data scope.
3. **Chart round-trip probe:** baseline grouped/stacked and combination chart models plus a non-Community family. Save, reopen, switch table/chart, refresh and recreate a chart widget in the same tab. Verify geometry, category ordering, values, series settings and navigator defaults/mutual exclusion. Fail on dropped fields or a semantically different chart. Expand only after a model is proven.
4. **Remote hierarchy probe:** a deterministic two-page endpoint with grouped/pivoted results and totals exceeding loaded rows. Compare baseline requests, expansion/collapse, sort/filter, page boundaries, failure/retry and selection/export scope. Fail if the candidate calculates full-dataset statistics from a page or changes backend request semantics.
5. **XLSX probe:** original export versus candidate for one styled financial table with grouped and filtered cases. Inspect workbook XML/cell types and values, then check actual Excel display where required by the inventoried behavior. Fail on textified numbers/dates, lost scale/format or changed scope.
6. **Open configuration probe:** one real payload for each original Highcharts constructor, plus supported options outside a proposed finite translator and an inventoried AI chart outside the current allowlist. Check builder autocomplete/save, import, raw-data toggle and interactions. A rejection proves the translator does not cover the original contract; do not count it as graceful parity.

Run later browser probes under [testing policy](../../steering/testing.md), isolated and initially one worker. This research authorizes none of their execution. Before accepting production edits, use the existing [complexity checks](../../../docs/complexity.md): 400 physical lines/file, 300 logical units/file and 50/function, whole modified maintained files, explicit fork scope. Cohesively extract oversized original hooks before modifying them; update the inventory and breadth map with actual checks. Production caps do not apply to this documentation-only report.

## Decision boundary

The engine-plus-compatibility approach is plausible for a finite, enumerated subset and is consistent with retaining the OpenBB interface. It is not a proven total replacement. The largest unresolved contracts are vendor-owned grid UI/gestures, SSRM hierarchy and open-ended chart configuration semantics. If probes fail, choices requiring an owner decision include funding a larger compatibility implementation, explicitly changing a documented contract, or revisiting the removal/library constraint. None is selected by this report; retaining commercial dependencies, hiding actions or silently narrowing supported inputs is not authorized. Renderer acceptance remains blocked until all original capability rows have equivalent outcomes or the owner explicitly changes the requirement.
