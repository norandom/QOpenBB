# Internal-only bridge publication: pinned source diagnosis

The official Moby source matching Docker 29.7.2 explains the observed missing host binding: a default NAT bridge endpoint attached only to an internal network is not selected as an external gateway, so its host-port binding requests are not programmed. This is a source-supported explanation for the observation, not an attestation that the local daemon executes an unmodified build of this source. More startup waiting has no source-supported mechanism to activate this binding while the topology stays unchanged.

This package is research only. It authorizes no runtime, browser, implementation, topology change, daemon change, or UI acceptance. Production Compose remains untouched. Research snapshots are excluded from production complexity caps; any later maintained implementation retains 400 physical lines/file, 300 logical units/file, and 50/function, with executable enforcement.

## Smallest next transport choices

Docker documents bridge access from the daemon host and same-network peers, default NAT mode, and loopback publication. It also explains that an ordinary internal bridge can still reach host services listening on its bridge address or all addresses. Thus internal networking does not mean isolation from every host service. [Official port-publishing documentation](https://docs.docker.com/engine/network/port-publishing/)

| Candidate | Scope and unresolved prerequisite |
| --- | --- |
| Direct daemon-host access | Smallest if an existing browser/client already shares the actual daemon host's reachable bridge namespace. Use the exact owned application address and port 3000. Windows/WSL CLI access alone does not establish that route; no firewall or routing changes are proposed. |
| Browser on the internal network | Same-network access avoids host publication and keeps the application internal-only. Requires a suitable existing browser runtime and ownership/cleanup review; no available image or dependency is assumed. |
| Fixed-destination test relay | Practical candidate when direct host access is unestablished: only the relay joins a normal bridge plus the application's internal bridge, and only the relay publishes a loopback endpoint. The application keeps its single internal endpoint. The relay forwards only to the exact owned application endpoint on port 3000, with no client-selected destination, CONNECT/general proxy, or routing-gateway function. This adds a dual-network peer and must not provide the application an external forwarding service. Source support for normal gateway publication and same-network access makes it plausible; end-to-end reachability and relay isolation remain unverified. |

The next bounded deliverable is a source-only fixed-destination relay proposal if direct-host access is not already established. Its essential boundary is the fixed application destination and unchanged internal-only application topology. This diagnosis does not implement the relay, install dependencies, grant a probe, or replace the existing lifecycle/egress/cleanup prerequisites. No UI or financial-content result follows from it.
